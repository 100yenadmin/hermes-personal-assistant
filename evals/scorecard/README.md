# VA scorecard

Run `python -m evals.scorecard --version V --commit SHA --lab DIR --as-of YYYY-MM-DD --out DIR`, optionally repeating `--lab` and `--live FILE` (one export per owner; duplicate baseline or day30 owner keys, and a task id repeated for one owner across files, are rejected). The JSON stores lab directory basenames only and names runs as `<lab basename>/<run folder>` in test run IDs, exclusions and fact errors; local paths are omitted. The Markdown omits paths and URLs. Only completed runs pinned to the full PA commit count (PA's `plugin-refs.json` entry is found by name, then by source, then first position; hand-built lab homes list heartbeat2 first), and partial checks never establish a full-area pass. Live task dates are ISO dates: the observed window runs from the first start to the earlier of the last due date and `--as-of` (tasks starting after `--as-of` are ignored), counting both endpoint days, and pending tasks count as failures only after their due date. A pass whose `closed_at` falls after its due date counts as a failure, and a task closed after `--as-of` counts as still open on that date. Each export carries its ledger's random `profile` id; two `--live` files with the same id are refused, whatever their owner labels. Missing owner baseline/day-30 records leave day-30 unproven; first-pass task types count distinctly. The command reports failures with exit 0 and rejects bad input with exit 2. Synthetic tests prove scoring rules, not real lab quality, publication, runtime activation or customer parity. Related issue: #48.

Catalogue tests may declare `covers`, a list of zero-based indices into their area's `duties`; it defaults to `[]` for every existing test. Only tests in state `pass` cover a duty. Each JSON area includes `uncovered_duties`, and the Markdown's "Unexercised duties" section lists those duties for every area, including areas with passing full tests. The headline always counts areas whose partial checks pass and areas whose partial checks fail (`· N areas with partial checks failing`, even at zero), and never a parity percentage.

Fail-closed input rules:
- A counted run needs a non-empty `overall` check map whose values are all `true`, and `all_pass` and the judge's `pass` must be the boolean `true`.
- Lab factual errors count from `fabricated_confirmations` and, where a fixture writes it, `factual_errors` (a number or a list).
- A run's identity is its scenario, `run_id` and `start` from `run.json`, so a renamed or copied folder is a duplicate. A `run.json` whose `start` is not a number, or whose `run_id` is not a string, is excluded as `malformed_run`.
- Live task ids must be unique per owner, text fields must not be blank, and every fact needs a non-empty `item` and `source`, internal facts included.
- Tasks starting after `--as-of` count for neither real work, facts nor the day-30 cohort.
- A day-30 record needs a `week_ending` date. It counts only when that week ends on or before `--as-of` and at least 28 days after the owner's first task; until then the owner's day-30 state is `unproven`.
- An area's parity stays `unproven` while any of its duties lacks a passing lab test.
- A damaged copy of a run never hides a valid one, because only counted runs reserve a run identity. A run missing `checks.json` or `judge.json` is `incomplete`, and one whose `run.json` scenario differs from `scenario.json` is `malformed_run`.
- Owner labels must not contain local paths, so owner keys stay distinct after scrubbing.
- Owner labels that differ only in case or spacing (including inner spaces) are refused, within one live file and across files, so one person never counts as two owners. Live fact errors name `owner/task-id`.
- A `run.json` `start` and `end` must be finite numbers. Two different lab directories with the same name are refused, because run ids name their directory; the same directory given twice dedupes.
- Markdown neutralises HTML, URLs (including protocol-relative and `mailto:`-style ones), link and image syntax, and local paths in values and JSON keys.
